# OCR2MD · 联邦最高宪法（AGENTS.md）

> **本文件是 OCR2MD 工作区根目录的联邦最高宪法。** 同级 `BUILD.md`、`COMM.md` 与 `GIT.md` 是联邦宪法的第二层专属契约，对根目录下全部 Main / Frame / Lab / 新版本强制生效。各项目自己的 `AGENTS.md` 是**州宪法**：独立 Git 文件、继承联邦所有强制要求，可在本州授权范围内补充和调适，但不能废止联邦条款。接手时先读联邦 `AGENTS.md` → 联邦 `BUILD.md` → 联邦 `COMM.md` → 联邦 `GIT.md` → **当前项目州级 `AGENTS.md`** → 该项目 `README.md`。尚在实验中的方案不得表述成 Main 已完成的事实。
>
> **联邦唯一权威**：根目录 `AGENTS.md` 由 Main Git 的 `main/constitution/AGENTS.md` 跟踪，两者须为同一真实硬链接 inode；根目录 `BUILD.md`、`COMM.md`、`GIT.md` 分别与 Main Git 的同名文件共用 inode。`main/AGENTS.md` 和每个 `labs/<lab>/AGENTS.md` 均是各州自己的独立、可版本化文件，不得与联邦或其他州共享 inode，也不得使用符号链接冒充继承。归档、审计快照及外部仓库不自动继承，须显式核对。

## 1. Git 留痕、可追溯回退

- 每轮有源码变更的构建或实验，无论成功失败，都要留下本地 Git Commit 检查点和测试／故障证据；提交说明回答“改了什么、为什么改、验证结果如何”。不另设与 Git 平行的变更台账。提交正文、证据及统一执法按同级 `GIT.md`。
- **每轮细步构建、一构建一 Git，发现 AI 实现偏离预期即停止该构建并回退，不允许在偏离版本上补丁式修复。** 具体回退/重启航点流程遵守同级 `BUILD.md`；先保全故障现场，只恢复最近实际验收正常的 SHA，不丢弃已验收成果。
- 日常开发与回退禁止使用破坏历史或现场的 git reset --hard、git clean、git rebase、git push --force；不得改写远端历史。历史构建不必长期保留多套发布目录，必要证据和 Git 历史须可追查。
- **通过相应 AM/Git 全量验收的开发分支**，必须按现行约定直接普通 push 至私有 GitHub，无须逐次请示；未验收的开发 Main 不得冒充正式发布分支。冻结的 audit/* 快照经基线预检与数据隔离核查后允许推送供外审，但不代表发布或通过验收。生产晋升仍需用户批准。

## 2. Main 开发发布与用户数据保护

- 每个活动版本有明确的主源码工作区和唯一正式发布目标；构建和发布必须对应可追溯 Git SHA。Main 与各 Lab 的工作树、运行数据、缓存和发布入口相互隔离。
- **Main 是持续开发验收版，不是生产版。** 修改完成必要的定向验证、留痕和构建后，直接更新内网及公网开发入口，**无需每次询问**。浏览器中未保存内容不构成开发版本发布门禁，也不得以此反复阻塞更新。
- 上述授权**不允许**清理、改写或覆盖磁盘中的用户文档、设置与媒体；正式生产环境仍须保护未保存编辑，且只有满足相应发布门禁才能称为正式验收通过。
- 回退使用已知正常源码重新构建发布；不依靠 A/B 常驻发布槽。具体命令、端口和路径放入当前版本实施文档，不写成永久规范。

## 3. 降低注意力负担，先验证再改动

- 只保留当前工作真正需要辨认的分支、目录、工具、入口和规则，不为防错堆叠重复系统。
- **州宪法与项目 README 双门禁**：每个独立项目、版本及活动 Lab 必须维护**独立州级 `AGENTS.md`** 和本工作树 `README.md`。州宪法必须明确继承根目录联邦全部登记契约并记录本州补充/调适边界；README 记录目标、架构、唯一数据权威、验收及未完成项。接手时必须读联邦宪法和当前州宪法，再读本州 README，不可用 Main 或其他 Lab 的文件代替；两者不得覆盖联邦约束。
- 按**明确目标与验收标准 → 运行现有实现 → 查看日志／证据 → 定位原因 → 最小修改 → 复跑 → 逐项验收**的顺序施工。未达到验收标准，不得宣称完成。
- 优先复用已验证的框架、组件和测试能力；不得因为一个局部问题重新制作平行的设置、导航、状态提示或数据管理系统。
- 失败允许在隔离环境中反复出现；**已验证成果必须可以累积，不因新实验而被悄悄侵蚀**。对失败提供证据、范围和恢复点，而不是仅靠 AI 记住上次教训。

## 4. 正式规范的授权边界

- 联邦宪法的正式原则只有用户明确授权才可新增、修改或删除。州级 AGENTS 可按本州明确授权补充与调适，但不得变更联邦条款、其他州规则或跨版本组件义务；跨州要求必须回联邦契约审议。一次功能试验不能自动取得永久规范授权。
- 本文件最多保留 **20 条一级编号原则**。需要扩张时先整合或取得用户批准，不得另建无编号规范或利用 README、Lab 专属 AGENTS 等绕过审批。
- Git 提交、模块设计、测试说明、AUDIT.md 及历史 ENGINEERING_MEMO.md 可以记录事实和执行细节，但不与本文件争夺规范优先级；历史技术决定须经当前代码与验收复核，不自动生效。
- 新 Lab / 新版本创建时必须先落地独立州 `AGENTS.md`、联邦继承声明及本州 README，自动门禁通过后才能开发；不能靠复制旧州宪法或硬链接到联邦规避继承检查。

## 5. 区分两类 Lab，避免伪镜像与功能重做

- **镜像型 Lab（候选版本）**：从指定 Main SHA 创建隔离 Git worktree，保持与该 SHA 的 Main 相同的业务模块图、公共 API、构建流程和验收标准。只有环境配置、URL、数据和输出位置可不同；不得通过 Lab 专有业务覆盖或重新接线绕过一致性。
- **框架型 Lab（独立实验）**：从 frame/base 或其他批准的实验基线建立，用于空白框架、组件与方案探索，例如 lab-frame、lab-ocr。这类 Lab 可以只装配实验所需模块，**不声称与 Main 完全镜像，也不得直接作为整个 Main 的晋升版本**。两类 Lab 的规则不可混用。
- 所有 Lab 使用独立工作树和文档／设置／缓存／发布路径；不得读写 Main 持久化数据，也不得以实验结果覆盖正式用户数据。同步基线采用正常 Git merge，保留冲突及修复记录。
- **镜像型 Lab 晋升**：冻结完整 SHA 与验收证据，以 fast-forward 或普通 merge 晋升 Main；禁止把已完成的 Lab 业务代码再手工复制、重做一套。若 Main 已前进，对合并后的最终 Main SHA 重跑涉及的集成验证；合并不等于自动通过生产审计。
- **框架型 Lab 产物采用**：以公开 API、直接测试和受控 Git 集成吸收已证明可用的模块或公共框架能力，先核对 Main 的实际装配与回归，再宣布采用；不能以 Lab 单独测试通过替代 Main 验收。
- 晋升后保留 Lab 实验数据与历史证据，后续在 Main 继续开发。镜像型 Lab 的执行细节见 docs/engineering/lab-lifecycle.md；该文档不适用于框架型 Lab 的整版本晋升。

## 6. 模块边界、唯一数据权威与变更影响测试

- 模块只暴露**少量、明确、稳定**的公开 API；模块间只通过登记的 API 或消息发布／订阅契约合作，不直接访问其他模块的私有状态、DOM、内部代码或持久化表来绕过边界。
- Git 版本化的 API 接口表和消息发布／订阅表是模块交互的正式契约，必须与实际定义、调用点及运行行为一致。**每个公开 API 都须有可独立执行的直接测试**；老模块逐步补齐，不以仅有集成测试冒充直接覆盖。
- 按 Git 变更影响范围进行**增量测试与边界审计**：API 定义、实现、依赖、调用方或测试变化时，验证受影响接口和跨模块联动；未受影响且有可复核 PASS 证据的范围可继承结论。涉及公共框架、契约迁移、晋升或发布门禁时，再按风险开展必要的更广回归，不机械地每次全文重测。
- 各数据域必须明确**唯一可写权威、原始输入的恢复方法、派生视图和回写路径**，避免 Markdown、编辑器缓存、SQL、AG/PDF 视图之间形成互相覆盖的平行真相。局部编辑应定位并更新受影响对象，不因单块变化默认全量刷新。MinerU JSON、SQLite、Markdown 等具体字段映射与同步策略由当前模块契约和测试定义，不能把未验收的试验 Schema 固化为全局规定。
- 已验证的公共设置、导航、状态栏及视图组件应通过正式 API 复用；新增相同职能的平行实现需要先证明现有契约无法满足需求。
- **Media 的 WP0～WP4 仅为参考范本，不是所有新模块必须重走的流程。** 具体模块验收以其自身公开契约和测试为准，不额外建立重复台账。

## 7. AM/Git 审计：保全成果，而非制造仪式

- 审计不仅运行功能测试，还要对照**实际源码、调用点、接口与消息登记、动态交互**检查是否越过模块边界；未覆盖、无法复现或动态路径不明的地方标记待核实／BLOCKED，不能报告 PASS。
- 一旦发现 AI 本轮构建偏离用户预期、越过既有模块边界或破坏已验收行为，先保存失败证据并定位引入提交，**立即终止该航点，使用可追溯 revert 或从已验收 SHA 建隔离工作树回退；不得在该偏离构建上补丁式修复**。需要重新实现，须从基线另开新的 Git 构建航点并重新验收。不能只靠补登记洗白，也不能牺牲其他已通过成果。
- 日常开发采用有证据的定向检查；需要独立全量审计时，固定 Main 的完整 Git SHA 和只读 audit/* 快照，内部 AI、Grok、Muse 按相同契约、夹具和验收口径独立检查与修复。各自报告保留 PASS、FAIL、BLOCKED 和未覆盖范围，不随 Main 更新漂移。
- Main 可以在定向验证后继续开发；审计修复分支经复核后正常合并，合并后的变更按影响面补审。旧 SHA 的审计结果不能冒充新 SHA 的生产验收。快照、分发、证据与报告格式依仓库 AUDIT.md 执行。

## 8. 空白框架、跨平台与可移植性

- **frame/base 是可复用的空白框架基线**；框架修复在该基线提交，独立功能实验从实验分支／worktree 开展。活动实验通过正常 merge 继承框架更新，冲突则停止核实，不强制覆盖；实验不得反向污染框架。
- 公共框架能力应从实验结果中明确提取、验证后再纳入 frame/base；实验模块要进入 Main，则遵循第 5、6、7 条的集成和验收规则，而非靠复制页面或改名为 Main。
- 面向支持的平台开发，个人绝对路径、单系统命令、固定浏览器路径和本地凭据不得写进通用业务源码；差异放到配置或独立适配层。
- Main 开发阶段先验证受影响的可执行环境，对尚无法运行的 Mac/Linux 或 Chromium/WebKit 项明确报告 BLOCKED；独立跨平台审计可与 Main 开发并行。**生产发布前**仍须满足适用跨平台、独立审计和数据隔离门禁，不得删测试或放宽断言来过关。


## 9. 统一 Lab 发布与访问入口

- **唯一共享发布面**：OCR2MD 所有可从 Lab 门户访问的实验版本，不论镜像型或框架型，统一使用仓库根目录 `release/` 和同一个 `/labs/` 门户／网关。模块静态产物放在 `release/<lab-id>/`，唯一发布登记源为 `release/release-manifest.json`，统一导航入口为 `release/index.html`。Main 也是 OCR2MD 的工作版本之一，但不拥有其他 Lab 的规则；任何 Lab 都不得把公共发布规则或唯一入口放进 Main 专属目录。
- **先登记，后可访问**：每个 Lab 使用稳定且唯一的 `lab-id`。首次发布必须同时具备对应静态产物目录、manifest 模块登记和门户入口；manifest 至少准确记录源 Git SHA、版本标识及每个发布文件的 SHA-256。统一网关按 manifest 校验文件后才提供访问。缺少登记、哈希不匹配或没有门户入口，都不能宣称该 Lab 已成功挂载。
- **同一 Lab 持续更新**：航点（WP）不是新的 Lab，也不创建新的发布目录。每次完成相应定向验证并提交 Git 检查点后，更新同一个 `lab-id` 对应的构建产物和 manifest 登记，让用户始终从同一个 `/labs/<lab-id>/` 入口打开最新实验版本；不因每个 WP 另建入口、Tunnel、网关或发布系统。首次挂载不必等到 WP15。
- **发布对象与运行数据隔离**：统一 `release/` 只承载经登记的静态发布产物；各 Lab 的 SQLite、文档、媒体、设置、Cookie、Token、缓存和日志仍留在各自隔离的运行目录／服务中。发布静态文件不得覆盖、搬移或重建这些运行数据，也不得触碰 Main 或其他 Lab 的用户数据。
- **发布前后核验**：发布源必须对应明确的 Git SHA；不得把未提交的工作树状态冒充已发布源码。发布后检查 manifest 中的 `sourceCommit`、版本和文件哈希，并从统一 `/labs/<lab-id>/` 入口实际打开页面，核对网关返回的发布身份与预期 SHA，验证入口资源可正常加载。只看到本地 build 成功或文件已复制，不算发布成功。失败时保留证据并恢复上一份已验证构建，不得留下半更新状态。
- **Lab 发布不等于验收或晋升**：Lab 发布只表示某个实验构建已进入统一 Lab 门户、可以实际打开；它不自动表示该 WP 验收通过、整个 Lab 完成、WP15 总体验收通过、晋升 Main 或生产发布。各 WP 按自身标准验收并留 Git 检查点；开发期间可持续更新同一个 Lab 入口。WP15、Main 集成／晋升及生产发布仍分别遵守各自门禁，不能互相替代。
- **旧式发布说明不得覆盖本条**：历史文档或脚本若描述把 Lab 静态文件发布到 Main 工作树下的独立 `/labs/<lab-id>/dist`、为单个 Lab 单独部署门户／网关，或另建发布根目录，该部分不再是当前统一 Lab 门户的发布目标。镜像型 Lab 的构建与模块图一致性检查可按对应实施说明执行，但最终 Lab 门户发布必须遵循本条的共享 `release/`、manifest 和统一入口约定；不得绕过 manifest 手工修改已发布模块文件。

## 10. 联邦 / 州宪法继承与同级联邦契约（最高规范）

- **联邦最高宪法**：OCR2MD **统一根目录** `AGENTS.md` 是所有子项目遵守的最高法律。Main Git 在 `main/constitution/AGENTS.md` 追踪同一硬链接实体，**Main 自己的 `main/AGENTS.md` 不是联邦宪法，而是 Main 州宪法**。
- **联邦同级契约**：根目录下受联邦 AGENTS 登记的 `BUILD.md`、`COMM.md` 和 `GIT.md` 是联邦宪法的正式组成部分，约束所有州；`README.md` 仅为工程导航。现行联邦目录：

  | 联邦文件 | 位置与权威 | 共同约束 |
  | --- | --- | --- |
  | **`AGENTS.md`** | 根目录联邦最高宪法；同 inode `main/constitution/AGENTS.md` | 权限、边界、州继承、Git/审计/发布上位规则 |
  | **`BUILD.md`** | 根目录与 `main/BUILD.md` 同 inode | 一构建一 Git、最小验收、偏离预期即回退而非补丁式修复 |
  | **`COMM.md`** | 根目录与 `main/COMM.md` 同 inode | Main/Frame/各 Lab 共同组件和 UI 交互、API 及门禁 |
  | **`GIT.md`** | 根目录与 `main/GIT.md` 同 inode | Git 提交正文、失败/回退/违宪证据、Notes 与统一执法 |

- **州宪法**：`main/AGENTS.md` 与 `labs/<lab>/AGENTS.md` 是**各自独立可修改的州法律**。所有州必须首先完整继承联邦 `AGENTS`、`BUILD`、`COMM`、`GIT`，可进一步规定本州独有的模块边界、数据权威、接口、发布方式和更严格的测试。州规定不能减弱联邦义务、不能跨州执法，不能借重命名或复制绕开 `COMM.md`；与联邦冲突则停止实施，由用户明确授权在有权层级处理。州 AGENTS 之间不得共享 inode，也不得与联邦根 AGENTS 共享 inode。
- **作用域与读取**：进入任意活动工作树先从统一根目录读取联邦 `AGENTS.md` → `BUILD.md` → `COMM.md` → `GIT.md`，再读**当前州** `AGENTS.md` → 当前州 `README.md`，最后读本州专属 API / 测试。跨入其他州需重新读取目标州 AGENTS；不得把 Main 州宪法强制用于其他 Lab。
- **唯一性与可执行门禁**：联邦四份文件只能由 Main Git 的登记路径追踪，不得在各 Lab 复制成可修改平行联邦文件。自动发现的 Main/所有活动 Lab 必须各自拥有非链接、与联邦不同 inode 的州 AGENTS；州文件继承声明指向统一根目录；既有 v1 三路径声明按联邦登记自动涵盖 GIT.md，不构成减免，新州声明增列 git 路径。根 `CROSS_VERSION_COMPONENTS.md` 仅为 `COMM.md` 的兼容链接，不构成独立联邦契约。任何继承断裂必须在布局检查中 FAIL；机器校验只能检查引用/身份，不能代替对实际州条文的冲突审计。
- **权限和历史**：修改联邦强制要求必须用户明确授权并记入 Main Git；州内独立规则只能在用户授权下通过该州 Git 提交、定向验收并 push。不得因修改州宪法重写联邦历史、其它州的文档或现存已冻结 Git tag。既有联邦同级契约发生矛盾时先停止施工，由用户裁决，不能以任一州的 README 或源码临时消解。
