# ocr2md 功能规范与功能调试协议

## 1. 目的

“功能调试”是产品功能的人工验收入口，不是 Agent 私有测试模式。

每一个产品功能都必须满足：

```text
功能规范
→ 真实产品实现
→ 功能调试固定样例
→ 自动 UIC / core 预检
→ 用户手动运行审核
```

自动测试通过不能代替人工审核；功能调试也不得实现一套只在调试模式存在的替代功能。

## 2. 功能规范的最小字段

每个功能项目至少写清：

| 字段 | 含义 |
| --- | --- |
| 功能 ID | 稳定编号，例如 `FC-EDIT-001` |
| 功能名 | 用户看到的功能名称 |
| 操作 | 用户实际操作什么 |
| 需要 | 执行前必须满足的状态、数据、模块或外部条件 |
| 效果 | 执行后用户必须看到的界面结果与数据结果 |
| 禁止 | 绝不能发生的副作用或错误行为 |
| 固定样例 | “功能调试”中如何独立复现 |
| 自动验证 | 对应 UIC / core tests |
| 人工审核 | 待审核 / 已通过 / 退回 |

“操作 / 需要 / 效果”三个字段不得省略，也不得只写实现细节。

## 3. 功能调试的强制行为

顶部“功能调试”用于逐项运行固定样例：

1. 每个功能项目必须可独立运行，不依赖先执行另一个功能样例。
2. 运行项目时可以内部恢复固定 fixture，但必须调用真实产品功能路径。
3. 不得用 debug-only flag 才启用真实功能。
4. 点击功能项目后应直接形成该固定样例的完整结果。
5. 项目执行后只禁用自己；“初始化”恢复全部样例。
6. 菜单中必须直接展示该功能的“操作 / 需要 / 效果”，供用户运行前核对。
7. 自动 UIC 只负责预检；最终状态由用户在真实页面手动审核。
8. 用户审核不通过时，先修产品实现或功能规范，不能修改测试来迁就错误结果。
9. **一个产品功能原则上只占一个功能调试入口。**复杂功能可以在该入口内部连续运行多个必要步骤，并用可见步骤条/进度状态展示过程；不得为了自动测试方便，把 Undo、Redo、分支失效等同一功能的子场景拆成多个菜单项。
10. 功能调试入口内部可以有多条自动 UIC 支撑，但这些 UIC 是测试组织方式，不应机械映射成多个用户可见菜单项。

## 4. 真实功能与功能调试必须共用一条路径

例如“行号菜单”：

错误：

```text
正常清洗工作区：点击行号无反应
功能调试：打开 debug flag 后点击行号才有菜单
```

正确：

```text
正常清洗工作区：点击行号 → 真实菜单
功能调试：只负责准备固定行/模块 → 调用同一个真实菜单和加入逻辑
```

因此，每个功能至少需要一条不依赖“功能调试”入口的产品 UIC；功能调试样例可以另外有一条 UIC。

## 5. Agent Definition of Done

一个新产品功能只有同时满足以下条件才算完成：

- 已登记功能规范；
- 已加入“功能调试”；
- 功能调试页面展示“操作 / 需要 / 效果”；
- 固定样例可独立运行；
- 正常产品路径可直接使用，不依赖调试入口；
- 可自动化部分已有 UIC / core 测试；
- 自动验证检查用户可见结果，而非只检查内部变量；
- 工程备忘已更新；
- 用户人工审核状态明确记录。

历史功能若尚未满足，必须在 `FEATURE_CATALOG.md` 中明确标为“待接入”，不得默认为完成。
